## 🌱 본질 메시지 — 진짜 핵심

### 시대의 본질 — Jensen Huang (NVIDIA CEO)

> *"You are now a software developer. Software development is dead. Everyone is now a software developer."*
> *"If everyone is a software developer, that means there's no differentiation way to make money from development."*

**해석:**
- *"개발자가 사라진다"* X → *"개발자 정의가 바뀐다"* O
- 코드 작성자 → AI 디렉터 / 검증자 / 결정자
- 차별화는 *"코드 잘 쓰기"* X → *"AI를 잘 쓰기"* O

### 표면 vs 실제

```
[표면 시각]
"AI가 코드를 대신 쓴다 = 사람은 일 안 해도 된다"

[실제 본질]
"AI가 비본질을 자동화하니 사람은 본질에 집중한다"
```

### 랄프톤 철학 (인용)

> *"인간은 놀고 AI는 일하게 만들고 난 잠 자고 오겠다.이 철학이니까."*
> — 랄프톤 SF 참가자

→ *"AI에게 위임 + 사람은 본질 사고"* 가 새 시대의 일하는 방식.

### 랄프 루프 — AI 협업의 본질 패턴

> *"라이프는 심슨 캐릭터인데 바보 같지만 우직하게 자기 할 일을 끝까지 해내는 캐릭터예요. 그래서 AI 에이전트한테 지금 네가 일을 한 번에 끝내지 못했더라도 강제로 그 루프를 돌리는 걸 랄프 루프라고 하거든요."*
> — 랄프톤 호스트

**해석:**
- AI 협업은 *"한 번에 완벽하게"* X → *"강제 반복 + 검증"* O
- 검증 시스템이 박혀있어야 *"랄프 루프"* 가 성립
- 검증 X 그냥 반복 = 무한 루프

→ **AI 협업 = 랄프 루프의 시스템화.** 검증 / 가드 / 패턴 누적이 그 시스템.

### 가제탈의 의미 — 자동화 실패의 시각화

영상에서 *"AI가 멈춰서 사람이 직접 컴퓨터 만지면 가제 코스튬 입어야 함"* 규칙은 단순 재미 X. **본질 메시지:**

```
"AI 자동화는 100% X.
 자동화 실패 시 사람이 개입하는 게 정상.
 단, 가제탈 입을 일을 줄이는 게 목표."
```

→ 메모리 / 가드 / 검증 시스템 = *"가제탈 입을 일 줄이는 도구"*. 100% 자동화 가정 X, *"실패 시 신속한 사람 개입"* + *"실패 빈도 감소"* 가 목표.

### 시간 제약 — 본질을 명확하게 만듦

영상 = 3시간 안에 결과 + 발표. 시간 제약은 *"제약"* 이 아니라 **본질 발견 도구**:

- 시간 무한 → *"하면 좋은 것"* 다 박음 → 본질 흐려짐
- 시간 유한 → *"꼭 해야 할 것"* 만 남음 → 본질 명확

→ Decision Budget 가드 / 카드 시간 cap = 본질 강제 명확화 시스템.

### 본질 5층 구조

```
[Layer 5] 본질 사고 (사람만)        — "내가 원하는 게 뭔가?"
   ↑
[Layer 4] 검증 시스템 설계 (사람)    — "AI 결과를 어떻게 검증?"
   ↑
[Layer 3] 결정 분기 (사람)          — "옵션 A vs B?"
   ↑
[Layer 2] 위임 설계 (사람)          — "AI에게 어떻게 위임?"
   ↑
[Layer 1] 실행 (AI 자동화)         — 코드 / 테스트 / PR / 문서
```

→ **사람의 가치는 Layer 5 → 1로 갈수록 높음.** AI 시대 시니어 = Layer 5 / 4 강한 사람.

## 🎯 핵심 원칙 5종

### 원칙 1: *"내가 원하는 게 뭔지"* 가 가장 중요

> *"가장 근본적인 문제는 나도 내가 원하는 것을 정확히 모르겠더라고요. 내가 원하는 걸 너무나 선명하게 잘 알고 있었다면 이걸 잘 적어서 하라고 시켰을 것 같은데."*
> *"사실은 나의 잘못인데 모델 탓을 하고 있었던 건 아닌가."*
> — 랄프톤 SF 참가자

#### 도구의 진화 = 본질 발견 능력의 진화

> *"진짜 원하는 것을 발견하고 그걸 할 수 있게 하는 도구들이 빠르게 좋아지고 있는 거 같아요."*
> — 랄프톤 SF 참가자

→ AI 도구의 가치는 *"코드 대신 써줌"* 이 아니라 *"네가 진짜 원하는 게 뭔지 발견하게 도와줌"*. 이걸 인지하면 AI 협업 방식 자체가 바뀜.

#### 시간 제약 활용

시간 무한 가정 → 본질 흐려짐. 시간 cap 박으면 *"꼭 해야 할 것"* 만 남음 → 본질 명확.

→ 카드마다 시간 cap 박는 게 본질 발견 도구.

**적용:**
- AI 결과가 이상하면 *"AI가 못 한다"* X, *"내가 명확히 못 표현했다"* O
- 카드 시작 전 *"나는 이 카드로 무엇을 얻고 싶은가"* 30초 자문
- 답 안 나오면 카드 자체를 다시 정의. AI에게 위임 X.
- 시간 cap 박아 본질 강제 명확화.

**자가 점검 질문:**
- 이 카드 끝나면 무엇이 가능해지나?
- 그게 진짜 내가 원하는 건가?
- 아니면 *"하면 좋아 보여서"* 박는 건가?
- 시간 cap 박혀있나?

→ **후자면 카드 폐기 또는 보류.**

### 원칙 2: *"리뷰 안 하면 망함"*

> *"리뷰를 잘 안 하시더라고요. 중간중간에 보니까 리뷰랑 엇나가는 부분들이 많았는데도 그냥 예스를 누르신 분들도 좀 계신 거 같고."*
> — 랄프톤 SF 심사 (이찬)

#### *"AI 컨트롤 밖"* 불안감 = 정직한 인정

> *"라이프가 많은 걸 스피드업은 해 주는데 제 컨트롤 밖에 있는게 너무 많아서 그거에 대한 불안감이 있지만 어쩔 수 없는 거 같아요."*
> — 랄프톤 SF 참가자

→ AI 자동화는 *"컨트롤 상실"* 이 본질적으로 따라옴. 이 불안을 **검증 시스템으로 답해야 함.** 검증 X → AI 신뢰 X → 시그널 0.

#### 가제탈 — 자동화 실패는 정상

AI 100% 자동화는 환상. 자동화 실패 시 사람 개입은 *"실패"* X, **정상.** 단 *"실패 빈도 감소"* + *"개입 신속"* 이 목표. 그래서 검증 시스템 + 가드 + 패턴 누적이 필수.

**적용:**
- AI 결과 *"문제 0건"* 이라 해도 한 번 더 검수
- 검수 X 그대로 머지 = AI 신뢰 X, AI 추천 그대로 사용 = 시그널 0
- 의심되면 *"이 부분 검증해줘"* 한 줄 던지기
- *"불안감"* 은 정상. 그 불안에 답하는 게 검증 시스템.
- 가제탈 입을 일이 발생해도 좌절 X. 발생 빈도 줄이는 시스템 박는 게 본질.

**자가 점검 질문:**
- AI가 한 결정 중 내가 본질 이해 못 한 게 있나?
- *"왜 이렇게 했지?"* 답 못 하면 검수 안 한 거.
- 면접관 / 동료 / 고객이 *"이거 왜 이래요?"* 물으면 답할 수 있나?

→ **답 못 하면 검수 미완료.**

### 원칙 3: *"평가 시스템 자체를 AI가 구축하게"*

> *"좋은 패턴들은 평가하는 것들 AI가 자체를 구축하게 해 가지고 체크하면서 제품 완성도 높여간 분들이 많았었는데."*
> — 랄프톤 SF 심사 (이찬)

**적용:**
- 단순 *"기능 박아줘"* X
- *"이 기능이 진짜 박혔는지 검증할 수 있는 시스템도 너가 만들어줘"* O
- 검증 → 학습 누적 → 다음 카드 적용

**검증 시스템 종류 (각 프로젝트마다 박힘):**
- **작업 패턴 누적 가이드** — 발생한 문제를 카테고리별 정리 + 사전 예방 명시
- **검증 체크리스트** — 박힌 기능이 진짜 박혔는지 grep / 테스트 / 명령어로 확인
- **기술 결정 근거 문서** — 후보 비교 + 트레이드오프 + 마이그레이션 트리거
- **의사결정 가드 / 패턴** — 무한 루프 차단 / 결정 마비 차단

**자가 점검 질문:**
- 이 카드에서 *"검증 시스템"* 도 같이 박혔나?
- 그 검증 시스템이 다음 카드에서도 작동하나?
- 작동 안 하면 시스템 X, 일회성 검증.

### 원칙 4: *"AI에게 연구하라고 시켜라"*

> *"AI can do a lot of things. You just need to ask it how it can. Ask it to research how it can achieve something."*
> — 랄프톤 SF 우승자 (Orchid 제작)

#### *"AI가 못 한다고 가정하지 마라"* — 비개발자에게도

> *"I have been telling my mom, hey, don't assume that I cannot. Ask you and ask it to figure out how can."*
> — 랄프톤 SF 우승자 (Orchid 제작)

**번역:**
> *"엄마한테도 말해. 'AI가 못 한다고 가정하지 마. AI에게 어떻게 할 수 있는지 알아오라고 시켜.'"*

→ **인지 전환이 본질.** *"AI가 못 한다"* 가정 X → *"AI에게 어떻게 할지 연구 시키기"* O. 이 인지 전환만으로 AI 협업 능력이 폭발적으로 증가.

#### *"시니어 → 주니어 멘토링"* 관점 (직관적 비유)

> *"그냥 고쳐줘 하면은 잘 안 되는 거 같고요. 내가 시니어라고 생각하고 주니어한테 어떻게 디렉션을 줘야 얘가 좀 더 잘 알아먹을까 그 관점으로 생각을 하는게 맞는 거 같아요."*
> — 랄프톤 SF 참가자

→ **AI를 "주니어 개발자"로 생각하고 시니어 관점에서 디렉션.**
- 주니어에게 *"고쳐줘"* 만 던지면 X. 맥락 / 의도 / 제약 / 우선순위 박아야 함.
- AI도 동일. *"X 만들어줘"* X → *"이 결과를 위해 X 방식으로 만들어줘. Y 위험 주의. Z 검증 필수."* O.

#### 첫 프롬프트의 4 요소 (랄프톤 심사 기준)

> *"첫 프롬프트가 중요하거든요. 어떤 작업을 맡길 건지, 어느 정도의 디테일을 담을 건지, 어떤 포인트들을 중요하게 생각하는지."*
> — 랄프톤 SF 심사 (이찬)

**첫 프롬프트 작성 4 요소:**
1. **무엇을 맡기는가** (작업 범위 / 결과물)
2. **디테일 정도** (얼마나 정밀하게 / 어디까지)
3. **중요한 포인트** (지켜야 할 제약 / 우선순위)
4. **어떻게 평가할까** (성공 기준 / 검증 방법)

→ 이 4 요소 박힌 첫 프롬프트가 *"심사 기준"*. 카드 시작 전 4 요소 자가 체크 권장.

#### 지시 vs 위임

- **지시 (낮은 레이어):** *"X 라이브러리로 Y 만들어줘"*
- **위임 (높은 레이어):** *"내가 원하는 결과는 [A]. 어떻게 달성할지 너가 연구해서 추천해줘."*

#### 5가지 위임 패턴

##### 패턴 1: 결과 명시 + 방법 위임
```
"내가 원하는 결과는 [구체 결과].
이걸 달성할 안전한 방법을 너가 측정해서 추천해줘.
사전 측정 항목 + 위험 시나리오 + 회귀 검증 방법까지."
```

##### 패턴 2: 평가 기준 + 결과물 위임
```
"평가 기준 = [A / B / C].
이 기준으로 우리 프로젝트 최적 [전략 / 패턴 / 라이브러리] 연구해서 추천해줘.
근거 + 후보 비교 + 트레이드오프 포함."
```

##### 패턴 3: 미래 시점 검토 위임
```
"6개월 / 1년 후 [사용자 N명 / 데이터 N건] 도달 가정.
지금 박은 [기술 / 결정]이 어떤 문제 일으킬지,
마이그레이션 비용 얼마일지 예측해서 ADR에 박아줘."
```

##### 패턴 4: 검증 시스템 위임
```
"내가 박은 [X]가 진짜 박혔는지 검증할 체크리스트 / 명령어를
너가 설계해서 자기 작업을 검증."
```

##### 패턴 5: 메타 분석 위임
```
"[면접관 / 동료 / 고객] 시각에서 우리 프로젝트가 어떤 질문 받을지,
답할 수 있는 근거가 코드에 박혔는지,
부족하면 어디가 부족한지 분석해줘."
```

**자가 점검 질문:**
- 이 카드 프롬프트가 *"지시"* 인가 *"위임"* 인가?
- 첫 프롬프트 4 요소 (작업 / 디테일 / 포인트 / 평가) 박혔나?
- *"주니어에게 디렉션 주는 시니어"* 관점인가?
- *"AI가 못 한다"* 가정하지 않고 *"어떻게 할지 연구 시키기"* 인가?
- AI 지식 한계 안에서만 작동하는가, 한계를 넘는가?

### 원칙 5: *"본질 결정은 AI가 못 한다"* + *"결정 근거 추적 필수"*

#### AI 결정 vs 사람 결정 — 명확히 분리

> *"PR 리뷰 시 *왜 이 DB 골랐어요?* 물으면 AI와의 대화를 추적해서 답할 수 있음. *AI가 추천했다* vs *개발자가 결정했다* 명확히 구분 가능. 같은 결정 반복 X."*
> — 랄프톤 SF 우승자 (Orchid 제작)

**해석:**
- AI 추천 그대로 채택 vs 개발자 본질 결정 = **명확히 분리해서 추적해야 함**
- 추적 X → 6개월 후 *"왜 이렇게 했지?"* 답 못 함
- 추적 O → *"이건 AI 추천 따랐고, 이건 내가 본질 결정했다"* 답 가능

→ **결정 근거 추적 시스템 (ADR / TECH_DECISIONS / 회의록) 박혀있어야 시니어.**

#### AI 가능 vs 불가 영역

**AI 가능 영역 (95%):**
- 코드 작성
- 테스트 / 검증
- 문서 / ADR
- 측정 / 분석
- 옵션 비교 / 추천

**AI 불가 영역 (5%):**
- *"내가 진짜 원하는 게 뭔가"* (Layer 5)
- 프로젝트 본질 / 가치 / 방향성
- 비즈니스 결정 (창업 / 구직 / 진로)
- 면접 / 발표 본인 답변

**적용:**
- AI는 본질 결정의 *"보조"* 까지만
- 옵션 분석 + 트레이드오프 + 추천 → AI
- 최종 결정 → 사람
- *"AI가 추천했으니까"* 가 사유면 결정 X
- 결정 근거 추적 시스템 박아두기 (6개월 후 추적 가능해야 함)

**자가 점검 질문:**
- 이 결정이 *"내가 원하는 거"* 에서 나왔나, *"AI 추천"* 에서 나왔나?
- 5년 후 본인이 봤을 때 *"왜 이 결정?"* 답할 수 있나?
- 결정 근거가 ADR / TECH_DECISIONS / 회의록 등에 박혀있나?
- AI 추천 그대로 vs 본인 결정 vs 트레이드오프 후 결정 — 명확히 구분되나?

→ **답 못 하면 본질 결정 X, AI 추종.**

## 🌐 프로젝트 본질 결정 — 시나리오 분류 가이드

모든 프로젝트는 시작 전 시나리오 결정 필수. *"시나리오 혼동"* 이 가장 위험.

### 시나리오 A: 기술 데모 / 포트폴리오
- 목적: 면접 / 이력서 / GitHub 어필
- 사용자: 0명 (포트폴리오 / 학습용)
- 핵심: *"기술을 어떻게 잘 박았나"*
- 방향성: 시니어 시그널 (시스템 설계 / 패턴 / 검증 시스템)
- 완성 조건: 기술 셋 정착 + 면접 답변 가능

### 시나리오 B: 실서비스 (개인 / 소수 사용자용)
- 목적: 진짜 사용자 1+ 명
- 사용자: 본인 / 지인 / 소수
- 핵심: *"내가 / 사용자가 실제로 쓰는 도구"*
- 방향성: 도메인 우선 (실제 워크플로우 자동화 / 통합)
- 완성 조건: 실 사용 발생 + 핵심 기능 안정

### 시나리오 C: SaaS / 비즈니스
- 목적: 수익 / 비즈니스
- 사용자: 다수 (B2C / B2B)
- 핵심: *"PMF (Product-Market Fit)"*
- 방향성: 사용자 인터뷰 / 니즈 검증 / MVP / 수익화
- 완성 조건: 유료 사용자 발생 / 매출

### 시나리오 결정 — 진입 트리거 3 질문

시나리오 B/C 진입 시 다음 3 질문에 답 가능해야 함:

1. **도메인 질문:** *"이 분야의 진짜 사용자가 진짜 겪는 문제 Top 5는?"*
2. **사용자 질문:** *"나는 이 서비스를 실제로 쓸 건가? 안 쓴다면 누가 쓸 건가? 5명 인터뷰해봤나?"*
3. **PMF 질문 (시나리오 C):** *"사용자가 N불 내고 쓸 가치 있나? 비즈니스 모델 + 수익화 경로?"*

→ **답 안 되면 시나리오 A로 끝내고 별도 프로젝트로 분리.**

### 가장 위험한 패턴 — 시나리오 혼동

```
"포트폴리오 + 실서비스 둘 다 잡으려다 어중간"
```

→ 명확히 분리. *"이 프로젝트는 시나리오 X입니다"* 답할 수 있어야 함.

**시니어 답변 예시:**
> *"이 프로젝트는 [기술 데모 / 실서비스 / SaaS] 목적이었어요.*
> *완성 조건은 [구체 조건]이고요.*
> *[다른 시나리오] 진입은 별도 프로젝트로 [도메인 검증 / 사용자 인터뷰 / PMF 검증]부터 시작할 거예요."*

→ **시나리오 분리하는 사람 = 시니어 시그널.**

- [ ] 내 프롬프트가 *"지시"* 인가 *"위임"* 인가?

### Level 4: 외부 시각 점검
- [ ] 면접관 / 동료 / 고객이 *"이거 왜 했어요?"* 물으면 답 가능한가?

- [ ] *"무엇을 원했나 → 후보 비교 → 선택 + 트레이드오프"* 박혀있나?

## 🧠 시니어 판단 패턴 (Aether 작업 회고 기반)

### 1. 카드 시작 전 사고 흐름 (5 단계)

| Step | 질문 | 산출물 |
|---|---|---|
| 1. 본질 질문 | "이 카드 끝나면 뭐가 가능?" | 한 줄 결과 정의 |
| 2. 시나리오 점검 | "A/B/C 어디 속하나" | 맥락 일관성 확인 |
| 3. 우선순위 | "지금이 적기? 다른 카드 먼저?" | 진입 시점 판단 |
| 4. 깊이 결정 | "Spike / 본격 / 보류" | 작업 분량 결정 |
| 5. 위임 설계 | "지시 X 위임 O" | AI 위임 방식 박음 |

**Aether 사례** — T-6 진입 시점에 "T-3 Multi-Agent vs T-6 Qdrant vs H-1d 정리" 비교 → T-6 채택. 이유: 차별화 강함(운영급 벡터 DB) + TECH §1 결정 근거 실증 + 시나리오 A 기술 데모 적합.

### 2. 위험 발견 시 분기 로직

| 위험 타입 | 정의 | 분기 |
|---|---|---|
| Type 1 (비가역) | 베이스라인 깨짐 / 데이터 손실 / 운영 중단 | **G1 트리거 즉시** + 선행 카드 분리 |
| Type 2 (가역) | 환경변수 토글 / 어댑터 / git revert 1줄 | 본질 조건 점검 후 결정 (보통 진행) |
| 후속 카드 분리 | 5분 이내 처리 X | 본 카드는 본질 작업만, 잔여는 후속 |
| 보류 결정 | 정보 부족 / 시나리오 불일치 | 보류 + 정보 수집 카드 |

**Aether 사례** — T-2 본격 PR 1차 시도 시 mcp 1.27 + fastapi 0.104.1 충돌 발견 → Type 1(비가역, 베이스라인 깨짐) 판정 → 즉시 Blocked + 선행 카드 H-X(베이스라인 일괄 업그레이드) 분리.

### 3. 카드 우선순위 판단 기준

- **차별화 (시니어 시그널 강함)** — 국내 도메인 사례 0건? 면접관이 *"이거 처음 보는 패턴"* 반응 줄 만한가
- **의존성 (선행 카드 있나)** — Blocked 상태 진입 시 G1 트리거
- **Big Bet vs 작은 결정** — 영향 범위 / 롤백 비용 / 학습 가치
- **시나리오 적합 여부** — A(기술 데모) / B(실서비스) / C(연구) 맥락 일치

**Aether 사례** — T-2(MCP) 우선순위 1번. 이유: 국내 도메인 MCP 서버 거의 0건 차별화 + AI Agent 시스템 핵심 + 외부 LLM 통합 표준 채택 = 시니어 시그널 3박자.

### 4. 본질 vs 비본질 구분 기준

| 본질 (해야 함) | 비본질 (보류 가능) |
|---|---|
| 시나리오 목적 직결 | "하면 좋아 보임" |
| 면접 답변 시그널 | 외부 시선 (보여주기) |
| 결정 근거 추적 가치 | 정리 / 미세 청결 |
| 차별화 / 위험 차단 | 완벽주의 |

**Aether 사례** — H-1d(`llm_max_tokens` 영구 해결) 보류 결정. 시나리오 A(기술 데모) 본질 X, *"정리하면 좋아 보임"* 영역. Top 10 종료 후 또는 사용자 컴플레인 발생 시 처리.

### 5. 메타 인지 패턴 (자가 점검)

- **무한 루프 자가 점검** — 5 가드 G1 본질 트리거 (시간 cap X, 본질 조건 O — 충돌 / 사용처 광범위 / 시그니처 호환 X / 차원 불일치)
- **본질 흐트러짐 자가 점검** — 자가 점검 4 레벨(L1 시간 / L2 본질 / L3 시나리오 / L4 메타)
- **결정 마비 인지** — 메타 사고 max 3 라운드 cap (그 후엔 가드 박고 직진)
- **가드 재점검 시점** — 카드 머지 후, 회고 시점에 가드가 본 카드에서 어떻게 작동했나 검수

**Aether 사례** — T-2 진입 직전 *"디벨롭 vs 직진"* 7 라운드 분석 → 결정 마비 인지 → 5 가드(메모리 #22) 박음 + 메타 사고 max 3 라운드 cap 박음. WORK_PATTERNS 문제 9로 정착.

### 6. 박지 않은 결정 = 명시한 결정만큼 강한 시그널

- **기술 도입** = 누구나 가능 (LangGraph supervisor / MCP / Multi-Agent 등)
- **시니어 차이** = *"박지 않은 결정 + 진입 트리거 명시"*
- **시나리오 본질 판단** → 부적합 시 보류 + 트리거 명시 (실서비스 진입 시점 등)
- **결정 근거 추적** (ADR 작성) = 6개월 후 본인 답 가능
- **학습 욕구 처리 — 적용 통합 본질**: 별도 학습 repo 만들지 않음 (재사용 어려움 + 가치 미흡). 학습 자료 링크 명시 + 진짜 적용 시점 (다른 프로젝트 / 시나리오 진입)에 학습 + 구현 동시 통합.

**Aether 사례** — T-3(Multi-Agent) 보류 결정(ADR 0010). 시나리오 A(기술 데모)에 과한 복잡도라 LangGraph supervisor + worker 패턴 도입하지 않음. 대신 *"Houseman Phase 7-12 진화 진입 시 학습 + 적용 통합"* 명시. Houseman 프로젝트도 동일 의사결정(메모리 #18) — 같은 패턴 두 프로젝트 일관 적용 = 결정 근거 추적 시스템 정착.

### 7. 본질 충돌 의심 시 두 본능 분리 검증

**증상:** 두 답이 충돌하는 것처럼 보임 (예: *"기술 때려박기 회피"* vs *"코드 디테일 학습 필요"*)

**진짜 본질:** 충돌 X, 맥락 다름. 분리 가능.

**3 단계 검증:**

1. 두 본능 명시 (*"본능 A: X, 본능 B: Y"*)
2. 충돌 vs 맥락 차이 검증 (*"진짜 충돌인가? 분리 가능한가?"*)
3. 분리 가능하면 둘 다 만족 (Stage 분리 / 시점 분리 / 영역 분리 등)

**답 흔들림 자가 인지:** 같은 주제에 답 2번 이상 바꾸면 본질 결정 근거 부족 신호. 즉시 멈추고 *"답 N번 흔들렸음, 본질 결정 근거 부족, 사용자 본능으로 결정 의무"* 보고. PRINCIPLES 원칙 5(본질 결정은 AI가 못 한다) 적용.

**Aether 사례** — T-3 보류 결정 흐름에서 *"별도 repo 도입 → 도입하지 마 → 다시 도입"* 답 3번 흔들림 발생. 본질 결정 근거 부족 인지 → 사용자 본능 *"Aether 기능 도출 X면 의미 없음"* 따라 최종 결정. 두 본능(*"기술 때려박기 회피"* vs *"코드 디테일 학습"*) 분리 가능 검증 → 시점 분리(학습 + 적용 통합 = Houseman 진화 시점)로 둘 다 만족.

---

> **요약** — 본 7 패턴은 *"코드 잘 쓰기"* 시그널이 아니라 *"AI 디렉터로서 의사결정"* 시그널. 면접관에게 *"이 사람은 카드 단위로 본질 사고하고 위험 분기하고 우선순위 판단하고 박지 않은 결정도 명시하는 사람"* 보여주는 메타 자료.
