## 통합 테스트에서 발견한 이슈 8개

### 이슈 1: ENV 변수명 불일치

택배를 "김철수"로 보냈는데 받는 쪽에서 "Kim Cheolsu"로 찾는 것.

```
docker-compose: GEMINI_API_KEY=abc123
llm-service: os.getenv("GOOGLE_API_KEY")  ← 이름이 달라서 못 찾음
```

docker-compose에서 보내는 이름과 서비스에서 받는 이름이 달랐다. 택배 수취인 이름을 통일해서 해결.

### 이슈 2: 포트 충돌

같은 건물에서 두 가게가 같은 호수(5432)를 쓰려는 것.

로컬 PostgreSQL이 이미 5432를 쓰고 있는데, Docker도 5432를 쓰려고 함. Docker 포트를 5433으로 변경해서 해결.

---

### 이슈 3: prometheus_client 모듈 누락

레시피에 "고추장 2스푼" 적어놓고 장보기 목록에 고추장을 안 적은 것.

코드에서 `import prometheus_client`를 쓰는데 `requirements.txt`에 안 적어서 모듈을 못 찾음. 장보기 목록(requirements.txt)에 추가해서 해결.

---

### 이슈 4: yfinance 429 Too Many Requests

"요청 너무 많아, 좀 쉬어" 거부당함.

Yahoo Finance에 주가 데이터를 너무 자주 요청해서 429(Too Many Requests) 에러. 오래된 yfinance 버전이 이 에러를 제대로 처리 못해서 업그레이드로 해결.

### 이슈 5: yfinance 1.x API Breaking Change

이전 버전: 숫자 목록 반환 → 새 버전: 엑셀 표 형태 반환.

```python
# 이전: Series (숫자 목록)
close = data["Close"]  # [100, 101, 102, ...]

# 1.x: DataFrame (엑셀 표)
close = data["Close"]  # 컬럼이 있는 표 형태
```

코드가 "숫자 목록이겠지" 가정 → 표가 와서 에러. `isinstance` 체크를 추가해서 두 형태 모두 처리하도록 수정.

### 이슈 7: ChromaDB 벡터 차원 불일치

DB에 768칸짜리 데이터 vs 새 모델 3072칸짜리 → "칸 수가 안 맞아!"

이전 모델이 768차원 벡터를 만들었는데, 새 모델은 3072차원을 만듦. 기존 DB에 넣으려니 크기가 안 맞음. DB를 비우고 새 모델로 재생성해서 해결.

### 이슈 8: async/middleware 충돌 (핵심)

식당에 요리사 1명(이벤트 루프).

```
async def = "멀티태스킹 할게!" 선언
실제 작업 = yfinance (네트워크 블로킹)
결과 = 요리사가 파스타만 30분째 저으며 모든 주문 대기 → 타임아웃
```

`async def`는 "나 멀티태스킹 할게!"라는 선언인데, 실제로 yfinance는 블로킹 작업(파스타 저으면서 다른 일 못함). 요리사가 파스타만 30분째 저으며 다른 모든 주문이 대기.

거기에 매니저(미들웨어)가 주문서(request body)를 미리 읽어버림 → 보조 요리사(라우터)가 주문서를 열면 이미 비어있음 → deadlock.

**해결:**
- `async def` → `def` (보조 요리사한테 맡김, FastAPI가 알아서 스레드 분배)
- 매니저가 주문서 안 읽게 변경 (미들웨어에서 body 소비 제거)

### 단위 테스트 vs 통합 테스트

| 비유 | 단위 테스트 | 통합 테스트 |
|------|------------|------------|
| 식당 비유 | 요리사 혼자 레시피대로 재료 써보는 것 | 실제 식당 열어서 손님 받아보는 것 |
| 발견 가능 | "이 레시피 계산이 맞나?" | "고추장이 장보기 목록에 없다" |
| 범위 | 함수 1개 | 서비스 전체 연결 |

→ "고추장이 목록에 없다", "문 번호가 겹친다", "멀티태스킹 중 멈춘다"는 식당을 실제로 열어봐야 알 수 있는 문제.

## ADR 8개 (기술 선택 근거)

### ADR-001: Redis Rate Limiting

진상 손님이 1초에 100번 주문 → 주방 마비.

| 선택지 | 비유 | 판단 |
|--------|------|------|
| A) In-Memory | 종이 메모 — 직원 바뀌면 까먹음, 지점 3개면 각각 10번 = 30번 허용 | 분산 환경 불가 |
| **B) Redis** | **중앙 출입 기록부 — 전 지점 공유, 10번 넘으면 1분 금지, 자동 리셋** | **채택** |
| C) API Gateway | 건물 경비원 — 경비원이 없어서 새로 고용 = 과도한 비용 | 인프라 과도 |

Redis sliding window: IP당 분당 10회 제한. 초과 시 429 + Retry-After 헤더.

---

### ADR-002: JWT 토큰 전략

4개 식당(마이크로서비스)을 돌아다니며 매번 "저 회원이에요" 증명.

| 선택지 | 비유 | 판단 |
|--------|------|------|
| A) Session | 카드를 식당에서 보관 — 보관함 고장 → 전원 인증 불가 | 서버 상태 의존 |
| **B) JWT** | **신분증 직접 소지 — 도장만 확인하면 끝. 분실 신고 목록(블랙리스트)으로 무효화** | **채택** |
| C) OAuth2 | 정부 여권 — 여권 발급소 운영 → 4개 식당 규모에 과도 | 복잡성 과도 |

- **Access Token** = 30분짜리 임시 출입증 (머릿속 = 메모리에)
- **Refresh Token** = 7일짜리 재발급 쿠폰 (지갑 = Redis에). 도둑이 쓰면 감지→전체 세션 차단

---

### ADR-003: Flyway DB 마이그레이션

메뉴판(DB 스키마) 변경 기록.

| 선택지 | 비유 | 판단 |
|--------|------|------|
| A) Hibernate auto | 그냥 고침 — 기록 없음, "카르보나라"+"크림파스타" 2개 생김 | 프로덕션 위험 |
| **B) Flyway** | **변경일지 간단 버전 — 일지 1호, 2호... 순서대로 적용. 새 지점도 1호부터** | **채택** |
| C) Liquibase | 변경일지 고급 버전 — 취소(롤백)도 가능하지만 메뉴 1개에 과도 | 기능 과도 |

`V1__init.sql`, `V2__add_column.sql` ... 번호 순서대로 자동 적용.

---

### ADR-004: Zustand 상태 관리

식당 4개 구역(페이지)에서 "이 손님 VIP인가?" 공유.

| 선택지 | 비유 | 판단 |
|--------|------|------|
| A) Redux | 중앙 관리 시스템 — 신청서→심사→등록 절차. 직원 2명인데 ERP 도입 | 보일러플레이트 과도 |
| **B) Zustand** | **벽 화이트보드 — "VIP" 적으면 끝. 특정 정보만 코팅(persist)** | **채택** |
| C) Recoil | 포스트잇 여러 장 — VIP 정보 5장 관리 → 과도 | atom 관리 과도 |
| D) Context | 구두 전달 — 전 구역 방송 → 전 직원 하던 일 멈춤(리렌더링) | 성능 문제 |

- `partialize` = 카드번호는 화이트보드에 안 적고 머릿속에만 (XSS 방어)
- `_hasHydrated` = "오픈 준비 완료" 신호 후 영업 시작 (hydration mismatch 방지)

### ADR-005: 토큰 저장 전략

VIP 카드를 어디에 보관?

| 선택지 | 비유 | 판단 |
|--------|------|------|
| A) localStorage | 지갑에 전부 — 소매치기(XSS) → 전부 털림 | 보안 취약 |
| B) httpOnly Cookie | 식당 금고 — 안전하지만 4개 건물(cross-origin)에서 열쇠 안 먹힘 | CORS 제한 |
| C) sessionStorage | 주머니 — 가게 나가면(탭 닫으면) 폐기, 옆 가게에서 인정 안 됨 | 범위 제한 |
| **D) 하이브리드** | **카드는 머릿속(메모리), 쿠폰만 지갑(localStorage)** | **채택** |

Access Token은 메모리에만 보관. 지갑(localStorage) 털려도 Refresh Token뿐. 쿠폰만으로는 입장 불가 (새 Access Token 발급 필요).

### ADR-006: Markowitz 포트폴리오 최적화

"1000만원 투자, 최적 비율 알려줘"

| 선택지 | 비유 | 판단 |
|--------|------|------|
| A) 균등 분배 | "333만원씩" → 최적화가 아니라 포기 | 수학적 근거 없음 |
| **B) Markowitz** | **과거 수익률+위험도 분석 → 최적 비율 계산. 노벨상 이론** | **채택** |
| C) Black-Litterman | 시장 전체+의견 결합. 정교하지만 복잡 | 구현 복잡도 과도 |
| D) Risk Parity | 동일 위험 부담. 안정적이지만 수익 최적화 불가 | 목적 불일치 |

3단계 보정 파이프라인:
1. **성적표 보정** (Ledoit-Wolf Shrinkage): 표본 공분산의 노이즈 감소
2. **검증** (Covariance Validation): 조건수, 상관계수, 양정치성 검사
3. **자동 수정** (Ridge Regularization): 문제 발견 시 대각선에 값 추가

### ADR-007: FastAPI async vs sync

주문 받으면 주방 멈추는 버그.

| 선택지 | 비유 | 판단 |
|--------|------|------|
| A) run_in_executor | 요리사가 직접 보조한테 시킴(to_thread) — 매번 "네가 해" 적어야 함. 빠뜨리면 또 멈춤 | 실수 위험 |
| **B) def (동기)** | **처음부터 보조한테 맡김 — FastAPI가 알아서 판단. async 키워드만 삭제** | **채택** |
| C) httpx async | 모든 재료를 택배로(비동기 HTTP) — 완벽하지만 전부 다시 짜야 함 | 리팩토링 과도 |

`async def optimize()` → `def optimize()`: FastAPI가 자동으로 스레드풀에서 실행. 이벤트 루프 차단 없음.

### ADR-008: Docker Compose 아키텍처

6개 구역 식당을 어떻게 여나.

| 선택지 | 비유 | 판단 |
|--------|------|------|
| A) 수동 실행 | 각 구역 따로 오픈 — 터미널 6개, "내 PC에서는 되는데" 문제 | 재현성 없음 |
| **B) Docker Compose** | **한 건물로 묶음 — `docker compose up` 한 마디. 순서 자동. 이름으로 통신** | **채택** |
| C) Kubernetes | 쇼핑몰 입점 — 입점 서류 20장 + 관리비 4GB. 6개 가게에 과도 | 인프라 과도 |

서비스 간 통신: `http://auth-service:8003` (컨테이너 이름 = DNS). `depends_on`으로 시작 순서 보장.

## BeforeAfter 6개 사례 요약

### 1. 비밀번호 무한 시도 → Redis로 "5번 틀리면 잠금"

| Before | After |
|--------|-------|
| 봇이 초당 수천 번 비밀번호 시도 가능 | Redis sliding window: IP당 분당 10회 제한 |
| 약한 비밀번호 몇 초면 뚫림 | 초과 시 429 + Retry-After |

---

### 2. 로그아웃해도 토큰 유효 → Redis 블랙리스트로 즉시 무효화

| Before | After |
|--------|-------|
| 로그아웃 후 Access Token 30분간 유효 | Redis 블랙리스트: 로그아웃 즉시 토큰 무효화 |
| 공용 PC에서 토큰 탈취 가능 | TTL = 잔여 만료시간 (자동 정리) |

---

### 3. 주식 비중 -30% 나옴 → 공분산 행렬 보정으로 정상 범위

| Before | After |
|--------|-------|
| 상관관계 높은 종목 → 가중치 -30% (공매도) | bounds=(0,1): 0~100%만 허용 |
| ill-conditioned 행렬 → 수치 불안정 | Ledoit-Wolf Shrinkage + Ridge Regularization |

---

### 4. 토큰 브라우저에 평문 저장 → 메모리에만 보관

| Before | After |
|--------|-------|
| Access Token이 localStorage에 평문 저장 | Access Token은 메모리(변수)에만 보관 |
| XSS 공격으로 탈취 가능 | Refresh Token만 localStorage (재발급용) |

---

### 5. API마다 토큰 수동 입력 → 자동 주입 + 만료 시 자동 갱신

| Before | After |
|--------|-------|
| 매 API 호출마다 `headers: { Authorization: ... }` 수동 입력 | Axios interceptor가 자동 주입 |
| 토큰 만료 시 에러 → 수동 재로그인 | 401 감지 → Refresh Token으로 자동 갱신 → 원래 요청 재시도 |

---

### 6. API 무한 대기 → async→def + 미들웨어 충돌 제거

| Before | After |
|--------|-------|
| `async def` + 블로킹 yfinance = 이벤트 루프 차단 | `def`로 변경 → FastAPI 스레드풀 자동 실행 |
| 미들웨어가 request body 소비 → 라우터에서 빈 body | 미들웨어 body 읽기 제거 → deadlock 해소 |
